# 다독임 요구사항

## 1. 문서 상태

- 작성일: 2026-08-31
- 상태: 사용자 확정 사항과 구체화 초안을 구분해 관리하는 진행 중 문서
- 프로젝트 이름: `다독임` (사용자 확정)
- 제품 관계: `inside-me`와는 별개의 독립 제품이다.
- 연동 가능성: 향후 사용자가 원할 때 `inside-me`에서 정리한 하루 일기와 감정을 이 제품의 긍정 확언 입력으로 전달할 수 있다. 현재 단계에서는 통합을 확정하지 않는다.

### 요구사항 기록 원칙

- `사용자 확정`: 사용자가 직접 말했거나 선택한 내용이다.
- `구체화 초안`: 사용자 설명을 실제 화면, 행동, 결과 형태로 풀어 쓴 내용이며 아직 최종 결정이 아니다.
- `제안`: 구현 가능성과 위험을 검토해 제시한 선택지이며 사용자 승인 전에는 확정하지 않는다.
- `미정`: 사용자의 선택이 필요한 내용이다.
- 이후 제품 의사결정은 `docs/decision-log.md`에 근거와 함께 기록한다.

### 현재 사용자 확정 범위

- `inside-me`와는 다른 독립 프로젝트로 만든다.
- 통합 프로젝트 이름과 한글 폴더명은 `다독임`으로 한다.
- 핵심 기능은 다음 세 가지다.
  1. 수면 유도용 음악·소리
  2. 긍정 확언
  3. 멍 때릴 때 듣는 음악·소리
- 요구사항 논의 및 개발 순서는 `멍 때릴 때 듣는 음악·소리(C) → 긍정 확언(B) → 수면 유도용 음악·소리(A)`다.
- C 요구사항을 먼저 사용자와 논의해 확정한 뒤 B를 논의하고, B를 확정한 뒤 A를 논의한다.
- C에서는 `안내 없이 듣기`와 `짧은 안내 후 듣기`를 모두 제공하고 사용자가 선택한다.
- C의 소리 선택은 `원하는 느낌으로 빠르게 추천받기`와 `전체 소리에서 직접 고르기`를 모두 제공한다.
- 앱 내부 코드는 `기능 중심 폴더 + MVVM식 역할 분리 + 단방향 상태 흐름`으로 구성한다.
- `inside-me`와 비슷하거나 확장처럼 사용할 가능성은 있지만 현재 하나로 합치지는 않는다.
- 제품과 구현에 관한 의사결정은 로그 파일로 남긴다.
- 구현 변경사항도 별도의 변경 로그 파일로 남긴다.

이 문서에서 위 범위를 넘어 구체화한 화면 흐름, 재생 시간, 사운드 종류, 기술 스택 및 구현 순서는 사용자 선택 전까지 `구체화 초안` 또는 `제안`이다.

### 시장 조사 상태

- 초기 경쟁 기능 조사는 `docs/market-research.md`에 작성했다.
- 아직 수행하지 않은 범위: 정량 시장 규모, 가격 비교, 실제 사용자 수요 검증.
- 처리 원칙: 공개 기능 비교에서 나온 차별화 방향은 `제안`이며, 사용자 선택과 사용성 검증 전에는 확정 요구사항으로 올리지 않는다.

## 요구사항 완성도 대시보드

> **현재 판정: 미완성 — 전체 제품 구현의 기준으로 사용할 수 없음**
>
> C의 일부 방향만 확정되었다. 미확정 항목은 `docs/open-questions.md`에서 관리하며, 사용자가 선택하기 전에는 요구사항이나 구현 기준으로 인정하지 않는다.

### 표시 기준

- `[x] 사용자 확정`: 구현 기준으로 사용할 수 있다.
- `[ ] 사용자 결정 필요`: 사용자가 선택하거나 승인해야 한다.
- `[~] 구체화 초안·제안`: Codex가 구체화하거나 추천했지만 사용자가 확정하지 않았다.
- `해당 없음·연기`: 사용자가 명시적으로 범위에서 제외하거나 이후로 미루기로 결정해야 한다.

### 영역별 완료 상태

| 영역 | 상태 | 완료를 막는 핵심 사항 |
| --- | --- | --- |

| C. 멍 때리기 소리 | 일부 확정 | 첫 소리, 느낌 범주, 안내·재생 상세, 완료 조건 |

### 미확정 사항 관리

- 현재 미확정 항목과 하나씩 선택할 질문은 `docs/open-questions.md`에서만 관리한다.
- 확정된 내용은 이 문서의 관련 기능 절에 반영하고, 결정 근거와 변경 이력은 DEC·CHG로 연결한다.
- 전체 미확정 목록을 이 문서에 중복하지 않는다.
- `docs/open-questions.md`의 모든 항목이 확정·제외·연기되면 해당 임시 파일을 삭제한다.

### 완료 판정 규칙

- 현재 논의 순서는 `C → B → A`를 유지한다.
- 각 항목은 사용자가 선택한 뒤 관련 DEC를 남기고, 확정 내용을 관련 요구사항 절에 반영한 다음 임시 작업판에서 제거한다.
- 사용자가 제외하거나 연기한 항목도 이유와 영향을 DEC에 남긴 뒤 임시 작업판에서 제거한다. 기록 없이 삭제하지 않는다.
- 모든 필수 항목과 기능별 완료 조건이 확정되고, 깐깐한 관리자 검수에서 `승인`되어야만 이 문서를 `완성`으로 바꿀 수 있다.

## 2. 제품 목적

> 상태: 첫 문단의 세 사용 상황은 사용자 요구를 요약한 것이다. 의료 서비스가 아니라 웰니스 도구로 한정하는 문장은 안전을 위한 구체화 초안이며 아직 사용자 확정 사항은 아니다.

사용자가 잠들기 전, 조용히 멍을 때리며 쉬고 싶을 때, 또는 오늘 있었던 일을 바탕으로 현실적인 긍정 확언을 듣고 싶을 때 필요한 소리를 간단하게 선택하고 재생할 수 있게 한다.

이 제품은 불면증이나 정신 건강 문제를 진단하거나 치료하는 의료 서비스가 아니다. 사용자가 마음을 정리하고 차분하게 쉬는 시간을 돕는 개인용 웰니스 도구를 목표로 한다.

## 3. 핵심 기능

### 기능 1. 수면 유도 음악·소리

> 상태: 기능의 존재만 사용자 확정이다. 아래 사용자 흐름과 세부 조건은 A 논의 차례에서 확인할 `구체화 초안`이다.

#### 사용자 목적

사용자는 잠자리에 누운 뒤 화면을 계속 조작하지 않고 차분한 음악이나 환경음을 들으며 잠들고 싶다.

#### 사용자 흐름

1. 사용자가 홈 화면에서 `잠들기`를 누른다.
2. 빗소리, 파도, 숲, 브라운 노이즈 등의 소리 중 하나를 선택한다.
3. 재생 시간과 음량을 선택한다.
4. 사용자가 재생을 시작하고 화면을 끈다.
5. 선택한 시간이 지나면 소리가 갑자기 끊기지 않고 서서히 작아진 뒤 종료된다.

#### 구체화 초안 — 검토 전 요구사항

- 화면이 꺼진 상태에서도 소리를 재생할 수 있어야 한다.
- 사용자는 재생, 일시 정지, 종료를 할 수 있어야 한다.
- 사용자는 15분, 30분, 60분 또는 계속 재생 중 하나를 선택할 수 있어야 한다.
- 종료 직전에는 소리가 서서히 작아져야 한다.
- 전화, 알람, 이어폰 연결 해제와 같은 상황에서 안전하게 재생을 멈추거나 복구해야 한다.
- 첫 버전의 사운드는 종류를 많이 늘리기보다 반복 지점이 거슬리지 않는 소수의 고품질 소리로 구성한다.

### 기능 2. 오늘의 일을 바탕으로 한 긍정 확언

> 상태: 오늘 있었던 일을 바탕으로 긍정 확언을 듣고 싶다는 목적만 사용자 요구에서 확인했다. 입력 방식, 생성 단계, 밤·아침 구분, 저장 방식은 B 논의 차례에서 확인할 `구체화 초안`이다.

#### 사용자 목적

사용자는 오늘 있었던 일을 글이나 말로 남기고, 그 경험을 부정하거나 과장하지 않는 긍정 확언을 만들어 잠들기 전과 다음 날 아침에 듣고 싶다.

#### 사용자 흐름

1. 사용자가 홈 화면에서 `오늘의 확언`을 누른다.
2. 오늘 있었던 일을 글로 쓰거나 음성으로 말한다.
3. 서비스가 사실, 감정 후보, 사용자가 한 노력, 현실적인 긍정 확언, 내일의 작은 방향을 제안한다.
4. 사용자가 각 문장을 확인하고 `사용`, `수정`, `제외` 중 하나를 선택한다.
5. 사용자가 승인한 문장만 음성으로 만들어진다.
6. 사용자는 목소리, 배경음, 전체 재생 시간을 선택한다.
7. 밤에는 승인한 확언과 배경음을 듣고, 다음 날 아침에는 핵심 문장과 작은 방향을 짧게 다시 듣는다.

#### 구체화 초안 — 확언 생성 원칙

- AI는 사용자의 감정을 단정하지 않는다.
- 사용자가 말하지 않은 사건이나 성과를 만들어내지 않는다.
- 힘들었던 일을 무조건 좋은 일로 바꾸어 해석하지 않는다.
- `나는 완벽하다`, `모두가 나를 좋아한다`처럼 현실과 지나치게 동떨어진 문장을 기본값으로 만들지 않는다.
- `사실 인정 → 감정 수용 → 사용자가 한 행동이나 노력 → 현실적인 확언 → 내일의 작은 방향` 순서를 기본으로 한다.
- 최종 문장 선택 권한은 사용자에게 있다.
- 사용자가 승인하지 않은 문장은 음성으로 재생하지 않는다.

#### 구체화 초안 — 검토 전 요구사항

- 글 입력을 지원해야 한다.
- 생성된 문장을 사용자가 직접 수정할 수 있어야 한다.
- 승인한 문장만 저장하고 재생할 수 있어야 한다.
- 밤용 오디오와 아침용 짧은 오디오를 구분해야 한다.
- 밤용 오디오에서는 일정 시간이 지나면 음성은 끝나고 배경음만 이어지도록 설정할 수 있어야 한다.
- 민감한 일기 내용은 기본적으로 기기에 저장한다.
- AI 처리가 필요할 때 어떤 내용이 외부로 전송되는지 사용자에게 알려야 한다.
- 기록과 생성된 오디오를 사용자가 직접 삭제할 수 있어야 한다.

### 기능 3. 멍 때릴 때 듣는 음악·소리

> 상태: 기능 목적, 안내 유무를 고르는 방식, 느낌 추천과 전체 보기의 두 선택 경로는 사용자 확정이다. 화면 문구, 상세 순서, 시간, 사운드 기준은 후속 결정이 필요한 `구체화 초안`이다.

#### 사용자 목적

사용자는 잠을 자려는 것은 아니지만 생각을 잠시 멈추고 아무것도 하지 않으며 쉬고 싶을 때 부담 없는 소리를 듣고 싶다.

#### 사용자 흐름

1. 사용자가 홈 화면에서 `잠깐 쉬기`를 누른다.
2. 사용자가 `안내 없이 듣기`와 `짧은 안내 후 듣기` 중 하나를 선택한다.
3. `짧은 안내 후 듣기`를 선택하면 짧은 호흡·이완 안내가 나온 뒤 음악·환경음만 이어진다.
4. 사용자는 첫 선택 화면에서 현재 원하는 느낌을 골라 소리를 빠르게 추천받거나 `전체 소리 보기`를 선택한다.
5. 느낌을 고른 경우 추천된 소리를 선택하고, `전체 소리 보기`를 고른 경우 전체 목록에서 원하는 소리를 직접 선택한다. 느낌 범주의 정확한 이름과 첫 소리 목록은 후속 대화에서 확정한다.
6. 재생 시간을 선택해 재생한다. 구체적인 시간 선택지는 후속 대화에서 확정한다.
7. 재생 중에는 복잡한 정보 없이 꼭 필요한 재생 정보와 종료 기능만 보여준다.

#### 사용자 확정 요구사항

- C는 수면 유도용 A와 별개의 `멍 때리며 쉬기` 기능으로 제공한다.
- 첫 소리 선택 화면에서 원하는 느낌에 맞는 소리를 추천받는 경로와 전체 소리를 직접 보는 경로를 모두 제공해야 한다.
- 사용자는 음성 안내를 원하지 않을 때 안내 없이 바로 음악·환경음을 들을 수 있어야 한다.
- 사용자는 원할 때 짧은 호흡·이완 안내를 들은 뒤 음악·환경음을 이어서 들을 수 있어야 한다.

#### 구체화 초안 — 검토 전 요구사항

- 5분과 10분처럼 짧은 휴식 시간을 지원한다.
- 화면 문구에서도 C의 목적이 수면 유도와 혼동되지 않게 구분한다.
- 가사나 큰 음량 변화처럼 사용자의 생각을 강하게 끌어당기는 요소를 기본 사운드에서 피한다.
- 사용자가 아무 기록도 남기지 않고 바로 재생할 수 있게 한다.
- 재생이 끝난 뒤 평가나 기록을 강요하지 않는다.
- 음성 안내의 길이, 내용, 건너뛰기 방식은 후속 대화에서 확정한다.

## 4. 홈 화면의 세 가지 진입점

> 상태: 세 기능의 존재는 사용자 확정이지만, 같은 수준의 홈 진입점과 화면 문구는 `구체화 초안`이다.

홈 화면에서는 세 기능을 같은 수준으로 보여준다.

1. `잠들기` — 수면 유도 음악·소리
2. `오늘의 확언` — 오늘의 경험을 바탕으로 만든 확언 오디오
3. `잠깐 쉬기` — 멍을 때리며 쉬는 음악·소리

사용자가 앱을 열었을 때 일기 작성부터 요구하지 않는다. 수면음이나 휴식 음악만 필요한 사용자는 즉시 재생할 수 있어야 한다.

## 5. 구현·출시 범위 상태

### 사용자 확정 범위

- 요구사항 논의와 개발은 `C → B → A` 순서로 진행한다.
- 현재 첫 구현 대상은 C지만, C의 세부 범위와 완료 조건은 아직 확정하지 않았다.
- 세 기능을 하나의 첫 MVP에 모두 넣을지는 아직 결정하지 않았다.

### 통합 MVP 후보 — 제안

- 세 가지 핵심 기능의 독립된 진입 화면
- 로컬 사운드 3~5개
- 재생, 일시 정지, 종료
- 재생 타이머와 점진적 음량 감소
- Android 화면 잠금 상태의 백그라운드 재생
- 긍정 확언 글 입력
- 확언 문장 생성, 수정, 승인, 제외
- 기본 한국어 음성으로 확언 재생
- 기록과 설정의 로컬 저장

### 후속 후보 — 제안

- 오늘 있었던 일의 음성 입력
- 사용자의 실제 목소리 녹음
- AI 음성 선택
- 사운드 두 개 이상 혼합
- 아침 알림과 아침용 확언 자동 재생 준비
- 오프라인용 오디오 미리 받기
- `inside-me` 기록 가져오기
- iOS 및 웹 지원

### 첫 버전 제외 후보 — 제안

- 수면 단계 측정
- 코골이 분석
- 심박수 및 웨어러블 연동
- 치료 효과를 보장하는 표현
- 커뮤니티 및 소셜 기능
- 결제와 구독
- 수백 개의 사운드 라이브러리
- 처음부터 여러 개의 독립 서버로 나누는 마이크로서비스 구조

## 6. `inside-me`와의 경계 및 향후 연동

### 현재 원칙

> 상태: 별개의 독립 제품이라는 점만 사용자 확정이다. 저장소·실행 앱·일정 경계의 세부 표현은 구체화 초안이다.

- 두 제품의 저장소와 실행 앱은 분리한다.
- 이 제품은 `inside-me`가 없어도 세 기능을 모두 사용할 수 있어야 한다.
- `inside-me`의 요구사항과 출시 일정이 이 제품 때문에 영향을 받지 않게 한다.

### 향후 가능한 연동 흐름

> 상태: 사용자 선택 전 `제안`이다.

1. 사용자가 `inside-me`에서 하루 이야기와 감정을 직접 확인하고 저장한다.
2. 사용자가 `이 내용으로 확언 만들기`를 명시적으로 선택한다.
3. 사용자가 승인한 요약만 이 제품으로 전달한다.
4. 이 제품에서 확언을 새로 생성하고 다시 사용자 승인을 받는다.
5. 승인된 확언을 밤용 또는 아침용 오디오로 재생한다.

### 중요한 데이터 원칙

> 상태: 개인정보 보호를 위한 `제안`이며 실제 연동 결정 때 확인한다.

- `inside-me`의 전체 일기 원문을 자동으로 가져오지 않는다.
- 사용자가 전달할 내용을 확인하고 승인해야 한다.
- 두 제품을 연동하지 않아도 각각 독립적으로 동작해야 한다.

## 7. 기술 방향 초안

> 상태: 제안. TypeScript, React Native, Expo 및 Android 우선 방향은 아직 사용자 확정 사항이 아니다.

### 확정된 앱 내부 구조

- 상태: 사용자 확정
- A·B·C와 공통 오디오를 기능 중심 폴더로 나눈다.
- 각 기능 안에서 `View`는 화면 표시와 사용자 입력, `ViewModel`은 화면 상태와 행동 조정, `Model`은 도메인 데이터와 규칙을 담는다.
- 상태는 `사용자 행동 → ViewModel의 상태 변경 → View 갱신`으로 한 방향으로 흐르게 한다.
- 전통적인 클래스형 MVVM을 강제하지 않고, 최종 프레임워크에 맞는 hook·store·state 구현으로 같은 역할 경계를 유지한다.
- 이 구조는 앱 내부의 코드·상태 구조 결정이다. 전체 배포 구조인 모놀리스·모듈형 모놀리스·MSA 중 어느 것을 쓸지는 아직 확정하지 않았다.

### 권장 클라이언트 기술

- TypeScript
- React Native
- Expo
- Android 우선

### TypeScript를 권장하는 이유

1. **데이터 모양을 코드에 명확하게 남길 수 있다.**
   예를 들어 수면 세션, 확언 문장, 휴식 사운드가 서로 다른 데이터라는 것을 타입으로 구분할 수 있다.

2. **AI가 작성하거나 수정한 코드의 실수를 실행 전에 더 많이 찾을 수 있다.**
   AI가 `durationMinutes` 대신 존재하지 않는 `duration`을 사용하거나, 밤용 확언과 아침용 확언을 섞었을 때 타입 검사에서 발견할 가능성이 커진다.

3. **코드의 의도가 AI에게도 문서처럼 보인다.**
   함수 이름만 있는 JavaScript보다 입력값과 결과 타입이 있는 TypeScript가 AI에게 더 많은 맥락을 제공한다. 다음 기능을 추가할 때도 기존 구조를 추측하는 범위가 줄어든다.

4. **화면, 저장소, 서버 사이의 계약을 맞추기 쉽다.**
   앱이 기대하는 확언 데이터와 서버가 돌려주는 데이터가 다르면 개발 단계에서 확인하기 쉽다.

5. **기능이 세 갈래로 늘어날 때 변경 범위를 추적하기 쉽다.**
   공통 오디오 플레이어를 수정했을 때 수면, 확언, 휴식 기능 중 어디가 영향을 받는지 확인하기 좋다.

TypeScript가 AI의 코드를 자동으로 올바르게 만들어주는 것은 아니다. 잘못된 요구사항, 부자연스러운 화면 흐름, 개인정보 처리 문제, 실제 기기에서만 발생하는 재생 문제는 타입 검사만으로 잡을 수 없다. TypeScript는 AI 코딩의 품질을 보장하는 도구가 아니라 실수의 범위를 줄이고 코드의 의도를 명확하게 만드는 안전장치다.

## 8. 서버 구성과 나중의 앱 통합 원칙

> 상태: 독립 프로젝트로 시작한다는 점을 제외한 서버·연동 방식과 현재 권장안은 모두 `제안`이다.

### 결론

두 프로젝트를 지금 독립적으로 개발한 뒤 나중에 하나의 앱에서 연결하는 것은 가능하다. 하나의 앱으로 보인다고 해서 서버도 반드시 하나여야 하는 것은 아니다.

### 가능한 방식

#### 방식 A. 독립 앱 유지 + 필요한 데이터만 전달

- `inside-me`와 이 제품을 각각 유지한다.
- 사용자가 선택했을 때 승인된 요약만 앱 링크 또는 API로 전달한다.
- 초기 연동 방식으로 가장 안전하다.

#### 방식 B. 하나의 앱 안에 두 기능 모듈을 넣고 서버는 분리

- 사용자에게는 하나의 앱으로 보인다.
- 앱 내부에는 감정 기록 모듈과 오디오 모듈이 따로 있다.
- 각 모듈이 기존 서버를 사용하거나, 앱 전용 중간 서버가 두 서버를 호출한다.
- 가능하지만 로그인, 장애 처리, 개인정보 정책, 배포가 복잡해진다.

#### 방식 C. 하나의 앱 + 하나의 모듈형 서버로 통합

- 사용자 계정, 기록, 확언, 오디오 기능을 하나의 서버 프로젝트 안에서 역할별 모듈로 구분한다.
- 개인 프로젝트 규모에서는 장기적으로 가장 단순할 수 있다.
- 실제 통합 필요성이 검증된 뒤 선택한다.

### 현재 권장안

- 지금은 이 제품을 독립 프로젝트로 만든다.
- 첫 MVP에서는 서버를 여러 개로 나누지 않는다.
- 가능하면 로컬 저장으로 시작하고, 비밀 AI 키나 음성 생성이 필요할 때만 작은 서버 경계를 추가한다.
- `inside-me` 연동은 나중에 `사용자가 승인한 하루 요약을 전달한다`는 작은 계약부터 시작한다.
- 두 제품을 정말 하나의 앱으로 자주 사용하게 된다는 사실이 확인된 뒤에만 화면이나 서버 통합을 검토한다.

## 10. 통합 MVP 완료 조건 초안

> 상태: `구체화 초안`이다. 현재 첫 구현 대상 C의 완료 조건으로 사용하지 않으며, A·B·C의 요구사항을 각각 논의한 뒤 다시 결정한다.

사용자가 Android 기기에서 앱을 열고 세 기능 중 하나를 선택할 수 있으며, 다음 세 시나리오가 각각 실제로 동작하면 첫 MVP의 핵심 흐름이 완성된 것으로 본다.

1. 수면음을 선택하고 화면을 끈 뒤에도 설정한 시간 동안 들을 수 있다.
2. 오늘 있었던 일을 쓰고, 생성된 문장을 수정·승인한 뒤 확언 오디오를 들을 수 있다.
3. 아무 기록 없이 짧은 휴식 음악을 선택해 5분 동안 들을 수 있다.
