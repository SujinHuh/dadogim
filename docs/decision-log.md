# 다독임 의사결정 로그

## 기록 규칙

각 결정은 다음 상태 중 하나로 기록한다.

- `확정`: 사용자가 직접 선택한 결정
- `제안`: 검토를 위해 제시했지만 아직 사용자가 선택하지 않은 내용
- `보류`: 지금 결정하지 않고 나중에 다시 검토할 내용
- `변경`: 이전 결정을 새로운 결정으로 교체한 내용

각 항목에는 사용자가 말한 내용, 선택지, 최종 결정, 선택 이유, 영향, 재검토 조건을 구분해서 남긴다. 사용자의 말과 제안 내용을 섞어 하나의 확정 사항처럼 기록하지 않는다.

## DEC-006. 의사결정 로그와 변경 로그를 항상 유지

- 날짜: 2026-09-01
- 상태: 확정
- 사용자 요구: 모든 의사결정과 변경사항을 로그로 남기고, 이 규칙을 프로젝트의 `AGENTS.md` 지침으로 만들고 싶다.
- 결정:
  - 제품 및 기술 선택의 이유는 의사결정 로그에 남긴다.
  - 파일, 기능, 설정의 실제 변경은 변경 로그에 남긴다.
  - 사용자 승인 전 제안은 `확정`으로 기록하지 않는다.
  - 변경으로 기존 결정이 바뀌면 이전 기록을 지우지 않고 새 항목에서 변경 이유를 연결한다.
- 적용 위치: 새 프로젝트 루트의 `AGENTS.md`에 영구 작업 규칙으로 추가한다.
- 현재 상태: 프로젝트 이름과 전용 루트 폴더가 아직 없으므로 실제 `AGENTS.md` 생성은 보류한다. 상위 `개인프로젝트/AGENTS.md`에 작성하면 다른 개인 프로젝트에도 적용될 수 있으므로 그 위치에는 만들지 않는다.
- 후속 상태: DEC-009와 CHG-007에서 전용 폴더와 `AGENTS.md`가 생성되어 위 보류 조건은 해소되었다.

## DEC-014. 기능 중심·MVVM식 역할·단방향 상태 흐름

- 날짜: 2026-09-01
- 상태: 확정
- 사용자 결정: `기능 중심 폴더 + MVVM식 역할 분리 + 단방향 상태 흐름 -> 이 구조로 가자.`
- 최종 결정: A·B·C·공통 오디오를 기능 중심으로 나누고, 각 기능에서 View·ViewModel·Model 역할을 분리하며 상태를 단방향으로 갱신한다.
- 선택 이유:
  - 기능 중심 폴더: `C → B → A` 순서로 기능을 하나씩 개발하면서 변경 범위와 PR을 작게 유지하고, 다른 기능에 미치는 영향을 줄이기 위해서다.
  - MVVM식 역할 분리: 화면 표시(View), 사용자 행동과 화면 상태 처리(ViewModel), 데이터·오디오 규칙(Model)을 구분해 각 부분을 이해하고 테스트하기 쉽게 하기 위해서다.
  - 단방향 상태 흐름: 재생·일시정지·선택·타이머처럼 상태가 자주 바뀌는 오디오 앱에서 변경 출처를 한 방향으로 추적해 화면과 실제 재생 상태의 불일치를 줄이기 위해서다.
  - 세 구조의 조합: 기능 경계와 역할 경계만으로는 상태 변경 경로가 모호할 수 있고, 단방향 흐름만으로는 기능별 코드 경계가 생기지 않으므로 세 가지가 서로의 빈틈을 보완한다.
- 구현 원칙: 특정 프레임워크의 클래스 형식을 강제하지 않고, 선택한 기술 스택에 맞는 도구로 같은 역할 경계를 유지한다.

- 영향: 이후 GitHub에 올리는 문서·코드·설정은 공통 템플릿과 `docs/pull-request-guide.md`를 따른다.

- PR 제목: `feat`, `fix`, `refactor`, `test`, `docs`, `build`, `ci`, `chore` 중 하나를 사용한 `영어 type: 한국어 제목` 형식을 유지한다. Draft는 제목 type이 아니라 GitHub 상태다.
- 검수 판정: DEC-017의 `승인`, `조건부 승인`, `반려`를 사용한다. 조건부 승인도 남은 조건이 해소되기 전에는 병합하지 않는다.
- 호출 시점: DEC-018의 제안을 채택한다. 요구사항 묶음 확정 후, 작은 구현·검사 후, 고위험 변경 전후, PR·병합 직전과 배포 직전에 검수하며 저위험 문서는 묶음 종료 시 한 번 검수한다.
- Action 경계: 자동 검사 규격은 확정했지만 실제 workflow 생성, 필수 상태 검사와 브랜치 보호는 `T-09B`에서 별도로 결정한다.
- 공식 근거: [Codex GitHub PR 리뷰](https://learn.chatgpt.com/docs/third-party/github)
- 후속 상태: DEC-029에서 실제 Action 검토를 첫 기능 일부 구현 뒤로 연기했다.

## DEC-028. 토큰 사용을 줄이는 에이전트·문서 환경 보강

- 날짜: 2026-09-05
- 상태: 제안
- 사용자 요청: Codex가 매 작업에서 불필요하게 많은 토큰을 쓰지 않도록 공식 OpenAI/Codex 자료에 근거한 환경을 먼저 제안한다.
- 추천안 A: 루트 `AGENTS.md`에는 항상 지켜야 할 짧고 영속적인 규칙과 문서 경로만 둔다. `docs/README.md`가 작업별 읽기 경로를 안내하고, 작업에서는 관련 절·DEC·CHG와 최근 항목만 읽는다. 기능별 규칙이 생길 때만 해당 코드에 가까운 중첩 `AGENTS.md`를 둔다.
- 선택지 B: 모든 상세 규칙을 루트 `AGENTS.md` 한 파일에 둔다. 찾기는 쉽지만 매 작업 입력이 커지고 기본 32 KiB 합산 한도와 지침 충돌 위험이 커 추천하지 않는다.
- 선택지 C: 오래된 로그를 주기적으로 요약·보관한다. 평소 입력은 줄지만 원본 이력 손실과 요약 왜곡 위험이 있어 append-only 원본을 유지하는 현재 정책에는 맞지 않는다.
- 추가 운영 제안: 같은 턴에서 변경되지 않은 문서를 반복해서 읽지 않고, `rg`로 관련 제목·ID를 찾은 뒤 필요한 범위만 읽는다. 상세 체크리스트는 작업 시에만 열며 같은 내용을 여러 문서에 복사하지 않는다.
- 공식 근거: [Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [Customization](https://learn.chatgpt.com/docs/customization/overview)
- 최종 결정: 미정. 사용자가 A·B·C 중 선택한 뒤에만 `AGENTS.md`의 강제 규칙과 문서 구조를 추가로 변경한다.
- 후속 상태: DEC-030에서 추천안 A를 확정했다.

## DEC-029. PR 검사 Action 도입 시점 연기

- 날짜: 2026-09-05
- 상태: 확정
- 사용자 결정: 현재는 코드와 실행 중인 서버가 없으므로 PR 검사 Action을 바로 사용하지 않는다. 코드가 완성되고 기능 일부가 동작하는 시점에 도입 여부를 다시 결정한다.
- 최종 결정: 제목·본문 자동 검사 규격은 문서에 보존하되 workflow, 필수 상태 검사와 브랜치 보호는 생성하지 않는다. 첫 기능 일부가 구현되어 실제 빌드·타입·테스트 명령이 정해진 뒤 `T-09B`를 재개한다.
- 이유: 검사할 코드와 반복 명령이 없는 현재 단계에서 Action을 먼저 운영하면 유지 비용만 생기고 실질적인 품질 증거는 늘지 않는다.
- 재검토 조건: C 기능의 첫 세로 조각이 구현되고 로컬에서 반복 가능한 검증 명령이 생겼을 때다.
- 영향: PR 템플릿과 깐깐한 관리자 검수는 지금부터 사용하며, 자동 검사가 없다는 사실을 PR에 명시한다.
