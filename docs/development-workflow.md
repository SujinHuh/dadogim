## 2. 공식 자료에서 반영한 원칙

- Codex는 작업 전에 `AGENTS.md`를 읽고, 프로젝트 루트에서 현재 폴더까지 지침을 합친다. 합산 크기는 기본 32 KiB 한도가 있으므로 루트 지침은 짧게 유지하고 세부 내용은 관련 문서로 보낸다. [공식 AGENTS.md 문서](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
- OpenAI 모델 가이드는 반복 지침과 예시를 줄이고 각 지침을 한 번씩만 쓰는 짧은 프롬프트가 토큰 효율과 품질에 도움이 될 수 있다고 안내한다. [공식 모델 가이드](https://developers.openai.com/api/docs/guides/latest-model)
- 서브에이전트는 독립 탐색·테스트·로그 분석을 병렬로 실행하고 메인 대화에는 요약만 돌려줘 맥락 오염을 줄일 수 있다. 다만 단일 에이전트보다 토큰을 더 사용하며, 쓰기 작업은 충돌 비용이 커질 수 있다. [공식 서브에이전트 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents)
- Git worktree는 각 채팅이 별도 체크아웃에서 독립적으로 작업하게 하지만 Git 저장소가 필요하다. [공식 worktree 문서](https://learn.chatgpt.com/docs/environments/git-worktrees)
- Codex 리뷰는 커밋·푸시 전 변경을 읽기 전용으로 검토하고 우선순위가 있는 지적을 제공할 수 있다. [공식 코드 리뷰 문서](https://learn.chatgpt.com/docs/code-review)
- OpenAI 내부 사례는 목표·승인 경계·명령·결과·해석·실패 경로·최종 결정을 작업 중에 기록하고, 이전 기록을 다음 실행에 재사용하는 흐름을 소개한다. [공식 Codex 블로그](https://developers.openai.com/blog/automating-repetitive-work-at-openai-with-codex)

## 3. 토큰 효율적인 문서·로그 운영

2. 요구사항은 A/B/C 전체가 아니라 현재 기능 섹션만 읽는다.
3. 로그는 ID 검색 또는 최근 항목부터 읽고, 이력 감사 요청이 있을 때만 전체를 읽는다.

### 쓰기

- 의사결정 로그: `ID·날짜·상태·사용자 결정·결론·근거·영향·재검토 조건`
- 변경 로그: `ID·날짜·변경 대상·핵심 변경·이유·관련 DEC·검증`
- 실패 기록은 다음 작업에 영향을 주는 경우에만 `시도·결과·판단·다음 방법`을 남긴다.
- 같은 배경을 요구사항·DEC·CHG에 복사하지 말고 서로 연결한다.

## 4. 모델 변경 시 지침

> 상태: DEC-016의 `제안`이다. 사용자 확정 전에는 강제 작업 규칙으로 적용하지 않는다.

OpenAI 공식 모델 가이드는 모델 전환 시 기존 프롬프트를 먼저 유지해 모델 변경만 비교하고, 대표 작업 평가 후 문제가 있을 때 프롬프트나 추론 설정을 작은 단위로 조정해 다시 평가하는 방식을 안내한다. 최신 모델은 기본 응답 길이와 추론 특성이 달라질 수 있으므로 기존의 짧게 쓰라는 지침이 여전히 필요한지도 실제 결과로 확인한다. [공식 모델 가이드](https://developers.openai.com/api/docs/guides/latest-model)

채택할 경우 다독임에서는 다음 순서로 적용한다.

1. 기존 모델, 대상 모델, 주요 설정과 비교할 대표 작업을 기록한다.
2. 지침·프롬프트를 고치지 않고 대상 모델로 같은 작업을 실행해 기준 결과를 만든다.
3. 필수 요구 충족, 누락, 정확성, 형식, 토큰, 지연과 비용 중 확인 가능한 항목을 비교한다.
4. 회귀가 있을 때만 지침·프롬프트 또는 추론 설정 중 하나를 조정한다.
5. 같은 대표 작업을 다시 실행하고 결과와 채택 여부를 기록한다.

`AGENTS.md`의 제품 목표·제약·승인 경계는 모델 공통 지침으로 유지한다. 특정 모델에서만 필요한 장황함, 추론 수준, 출력 형식 보정은 공통 규칙과 분리하고, 실제로 측정된 차이가 있을 때만 추가한다.

## 5. 병렬 개발 전략

### 우선 병렬화 대상

- 서로 독립적인 코드베이스 탐색
- 독립 테스트 그룹과 정적 검사
- 리뷰 관점 분리: 정확성, 테스트 누락, 보안·개인정보, 유지보수성
- 대량 로그·자료 분석 후 요약 수집

### 제한과 현재 제약

- 같은 파일이나 같은 공통 인터페이스를 여러 작업자가 동시에 수정하지 않는다.
- 작업별로 입력, 소유 파일, 기대 출력, 종료 조건을 먼저 정하고 메인 작업자가 통합 테스트와 최종 diff를 확인한다.
- 작은 단일 파일 수정에는 서브에이전트를 사용하지 않는다.
- 현재 `다독임`의 Git 루트는 상위 `/Users/huhsujin/Documents/Playground`다. `다독임`을 별도 저장소로 초기화하기 전에는 이 프로젝트 전용 worktree 병렬 쓰기를 사용하지 않는다.

## 6. 작은 작업·PR·사용자 리뷰

- PR 하나는 하나의 사용자 행동, 버그 수정, 기술적 기반 중 하나만 완결한다.
- 크기는 줄 수보다 `별도로 설명·테스트·롤백할 수 있는가`로 나눈다. 정량 상한은 사용자와 후속 결정한다.
- 기능 변경과 직접 관련 없는 리팩토링·이름 변경·일괄 포맷은 별도 작업으로 나눈다.
- 사용자 검토 전에 `변경 목적 / 파일별 변경 / 보이는 행동 차이 / 검증 / 위험·미확인 / diff 보기 경로`를 보여준다.
- 사용자 승인 전에 커밋·푸시·PR 생성을 하지 않는다.

## 7. 리팩토링·클린 코드 검토

- 의도가 보이는 이름과 작은 역할의 함수·모듈을 사용한다.
- 사용하지 않는 코드, 중복, 숨은 부수 효과, 불필요한 추상화를 늘리지 않는다.
- 오류 경로와 외부 입력을 명시적으로 다루고, 개인정보·일기·오디오를 로그에 노출하지 않는다.
- 리팩토링이 외부 행동을 바꾸지 않았는지 행동 보존 테스트로 확인한다.
- 포맷, 린트, 타입 검사, 테스트, 빌드 중 현재 스택에 해당하는 검사를 실행한다.
- diff를 별도 리뷰하고 정확성, 회귀, 테스트 누락, 보안·개인정보, 복잡도 증가 순으로 확인한다.

## 8. GitHub Issue 발견·기록 전략

### 발견 경로

1. 요구사항 인수 조건과 수동 시나리오
2. 포맷·린트·타입 검사·단위/통합 테스트·빌드
3. 실제 기기의 백그라운드 재생, 전화·알람·이어폰 해제, 화면 잠금 검증
4. 커밋 전 로컬 diff 리뷰와 PR 리뷰
5. 의존성/보안 경고, 런타임 오류, 사용자 제보

### 이슈 템플릿

- 유형: `확인된 버그 / 의심 사항 / 개선 / 기술 부채 / 보안·개인정보`
- 증거: 환경, 재현 절차, 실제 결과, 기대 결과, 로그·스크린샷·실패 테스트
- 영향: 사용자 영향, 데이터·개인정보 위험, 발생 빈도, 우회 방법
- 추적: 관련 requirement, DEC, CHG, PR, 재검증 결과

재현 증거가 없는 내용은 `확인된 버그`로 표시하지 않는다. GitHub Issue 생성은 외부 쓰기이므로 먼저 초안을 보여주고 사용자 승인 후 생성한다.

## 9. CI/CD·GitHub Actions 단계별 전략

### 0단계: 스택 확정 전

- 워크플로를 생성하지 않고 인수 조건과 필수 검사 목록만 유지한다. PR 제목·본문 자동 검사 규격은 `pull-request-guide.md`에 확정했지만 실제 Action은 코드와 첫 기능 일부가 생겨 검사할 빌드·타입·테스트 명령이 정해진 뒤 `T-09B`에서 다시 결정한다.

### 1단계: PR CI

- 도입 시점은 코드와 첫 기능 일부가 완성되어 반복 실행할 실제 검증 명령이 생긴 뒤다.
- 잠금 파일로 의존성을 설치한다.
- 포맷 검사, 린트, 타입 검사, 단위 테스트, 빌드를 서로 독립적일 때 병렬 실행한다.
- 필수 검사가 모두 통과해야 merge하고, 로그·산출물에 비밀값·일기·오디오 내용을 남기지 않는다.

### 2단계: 내부 프리뷰

- `main`이나 배포 브랜치 합치기 후 테스트용 아티팩트를 생성한다.
- 실제 기기 검증은 자동 빌드 성공과 별도로 사용자가 확인한다.

### 3단계: 제작 배포

- 버전 태그, 변경 요약, 필수 CI, 사용자의 명시적 배포 승인을 게이트로 사용한다.
- 실패 시 자동 재시도 횟수와 롤백 방법을 먼저 정한다.

### Codex GitHub Action

공식 `openai/codex-action@v1`은 PR 피드백, 품질 게이트, 반복 작업을 GitHub Actions에서 실행할 수 있다. 다만 API 키·사용량·권한 설정이 필요하므로 선택 사항으로 둔다. 먼저 일반 CI의 결정적 검사를 구축하고, Codex 리뷰는 추가 검토로만 사용한다. [공식 Codex GitHub Action 문서](https://learn.chatgpt.com/docs/github-action)

## 10. 코드 리뷰 전략

- 로컬에서 커밋 전 `uncommitted diff`를 리뷰한다.
- PR에서는 베이스 브랜치 대비 변경만 보고 인수 조건과 리뷰 관점을 함께 제공한다.
- GitHub 연동 후에는 `@codex review`나 자동 리뷰를 선택적으로 사용할 수 있다. 저장소 특화 리뷰 규칙은 `AGENTS.md`에 2~3개의 짧고 영속적인 규칙으로 유지하고, 기계적 검사는 CI에 맡긴다. [공식 GitHub 코드 리뷰 문서](https://learn.chatgpt.com/docs/third-party/github)
- AI 리뷰는 테스트, 브랜치 보호, 사용자의 최종 검토를 대체하지 않는다.
- 깐깐한 관리자 검수의 입력, 순서와 결과 형식은 `review-guide.md`를 단일 원본으로 사용한다.

## 11. 깐깐한 관리자 검수자

### 역할 — 사용자 확정

- 구현자의 설명을 믿고 통과시키지 않고 요구사항, diff, 실행 증거를 서로 대조한다.
- `아마 동작함`, 정적 검사만 통과, 사용자 미확정 제안 구현, 테스트하지 않은 실제 기기 행동은 완료로 승인하지 않는다.
- 오류를 찾으면 심각도, 근거, 사용자 영향, 필요한 교정을 제시하고 교정 후 같은 항목을 다시 검증한다.
- 판정은 `승인`, `조건부 승인`, `반려`로 명확히 남긴다.

### 호출 시점 — 사용자 확정

1. 기능 요구사항 묶음 확정 직후: 구현 전에 범위·모순·누락을 반려할 마지막 지점
2. 작은 작업 구현과 관련 검사가 끝난 직후: 사용자에게 diff를 보여주기 전 독립 검수
3. 아키텍처, 개인정보, 사운드 이용 권한, 오디오 백그라운드 동작을 바꿀 때: 영향 범위가 큰 변경의 사전·사후 검수
4. PR 또는 병합 직전: 요구사항·테스트·변경 로그가 실제 diff와 일치하는지 확인
5. 배포 직전: CI 결과와 실제 기기 핵심 시나리오를 분리해 최종 판정

오탈자 하나처럼 행동에 영향이 없는 변경마다 호출하면 비용만 늘어난다. 저위험 문서 수정은 한 작업 묶음이 끝날 때 한 번 검수하고, 제품 행동·데이터·권한·배포가 바뀌면 즉시 호출하는 방식을 추천한다.

호출 시점과 비용 조절은 DEC-027에서 확정했다. `승인`, `조건부 승인`, `반려`의 판정 기준과 재검수 절차는 `review-guide.md`를 따른다.
